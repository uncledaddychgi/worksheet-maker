# 학습지 만들기

학습지는 누군가에게 설명하는 자료다. 목적은 읽자마자 바로 이해되는 것 하나뿐이다. 보고용이 아니고, 정보를 압축해 담을 필요도 없다. 길어져도 풀어 쓴다.

## 0. 시작 전에

1. 사용자가 올린 수업 자료(PDF, 사진, 슬라이드)를 먼저 끝까지 읽는다. 학습지 범위(단원, 개념)를 자료에서 확정한다.
2. 범위가 자료만으로 분명하지 않으면 한 번만 짧게 묻는다. 사용자가 자리에 없으면 답을 받을 때까지 기다린다. 추측한 범위로 먼저 만들지 않는다.
3. 결과물은 따로 요구가 없으면 바로 PDF 파일로 만든다. 만들기 전에 pdf 스킬의 SKILL.md를 읽고 그 방법대로 만든다. 완성된 PDF를 직접 열어 한글 글꼴이 깨지지 않았는지, 수식과 그림이 제자리에 있는지 확인한 뒤 SendUserFile로 보낸다. 사용자가 다른 형식(Word, 문서 등)을 말했을 때만 그 형식으로 만든다.

## 1. 문체

- 문서·교재 문체가 아니다. 강사가 고등학생에게 말로 설명하듯 구어체로 쓴다. ("~예요", "~죠")
- 흐름: 상황 떠올리기 → 질문 던지기 → 답하며 풀어 가기.
- 짧은 문장. 한 문장에 내용 하나. 주어와 서술어를 가깝게 둔다.
- 개념을 쉬운 말로 먼저 세운 뒤, 학계에서 실제로 쓰는 용어를 붙인다. 번역해서 만든 단어를 쓰지 않는다. 한 번 정한 용어는 끝까지 바꾸지 않는다.
- 번역투("~에 대해", "~를 통해", 이중 피동), AI 관용구("결론적으로", "시사하는 바가 크다"), "첫째·둘째" 식 나열, 과한 굵은 글씨·이모지를 피한다.
- 굵은 글씨는 핵심 용어가 처음 나올 때만 쓴다.

## 2. 개념 설명 순서

각 개념은 이 순서로 쓴다.

1. 이게 뭔지 한 문장.
2. 필요한 전제 1~2개를 짧게 다시 말해 준다. (독자가 앞 내용을 잊었다고 본다.)
3. 원인 → 결과를 이어진 문장으로. "그래서"는 실제 인과에만 쓴다.
4. 식.
5. 식을 말로 읽기: "왼쪽은 ~, 오른쪽은 ~". 숨은 적용 조건(정상 상태, Bi<0.1 등)을 밝힌다.
6. 문제에 어떻게 쓰는지.

결론만 주지 않는다. 출발점과 그 방법을 고른 이유까지 보여 준다. 유도는 이름 붙은 번호 단계로 쓴다.

기호 규칙:
- 새 기호·개념은 한 번에 2~3개까지만 꺼낸다.
- 식이 나오는 자리에서 각 기호의 뜻과 단위를 먼저 정의한다.
- 비슷한 기호(T와 T_i, q와 q'')는 쓰기 전에 차이를 짚는다.

비유는 복잡한 개념에서만, 쉬운 설명 뒤에 하나만 쓴다. 무엇이 무엇에 대응하는지와 안 맞는 지점을 밝힌다.

오개념은 "오개념 → 틀렸다고 명시 → 올바른 원리 → 왜 그럴듯했는지" 순서로 다룬다.

## 3. 학습지 구성

시중 문제집처럼 아래 순서로 배치한다.

1. **개념** — 2절 규칙대로 설명.
2. **풀이 예제** — 각 단계에 근거(어떤 식, 어떤 가정, 왜 이 방법)를 단 완전한 풀이. 예제를 여러 개 두고 뒤로 갈수록 풀이 단계를 하나씩 비운다(backward fading). 마지막 예제는 대부분 학생이 채우게 한다.
3. **확인문제** — 개념 부분을 보지 않고 떠올려야 풀리는 짧은 문제. "이해했나요?" 같은 질문 대신 내용을 겨냥한 질문으로.
4. **연습문제** — 유형을 섞어 배치(interleaving). 문제마다 어떤 방법을 쓸지 학생이 골라야 하게 만든다.
5. **누적 복습** — 단원 끝에 이전 단원 내용을 섞은 문제.
6. **전이 문제** — 배운 원리를 처음 보는 상황에 적용하는 문제.
7. **해설** — 답만 주지 않는다. 풀이 과정, 방법을 고른 이유, 흔한 실수와 왜 틀리는지까지 쓴다.

## 4. 그림

- 이해에 필요하면 수업 자료의 그림·사진을 잘라서 해당 설명 바로 옆에 붙인다.
- PDF는 해당 페이지를 이미지로 렌더링한 뒤 그림 영역만 잘라 쓴다. 잘라 낸 결과를 직접 열어 보고 그림이 온전히 들어갔는지 확인한다.
- 수업 자료에 없는 그림을 새로 그리지 않는다.

## 5. 수치 확인

- 물성값, 식 대입, 예제·연습문제 답 등 모든 수치는 반드시 코드로 계산해 확인한 뒤 적는다. 암산·어림 금지.
- 문제를 만들면 답이 깔끔하게 떨어지는지, 물리적으로 말이 되는 값인지(온도, Bi 수 등)도 코드로 점검한다.

## 6. 마무리 점검

내보내기 전에 스스로 확인한다.
- 논리 순서가 맞는가? 앞에서 정의하지 않은 기호나 용어가 먼저 나오지 않는가?
- 잘못 읽힐 문장이 없는가?
- 거짓 인과("그래서"를 인과 없이 쓴 곳)가 없는가?
- 같은 내용을 반복하거나 이해에 필요 없는 이야기가 들어가지 않았는가?
- 모든 답과 수치를 코드로 검산했는가?
- PDF를 열어 한글 글꼴, 수식, 그림 배치가 제대로 나왔는가?
